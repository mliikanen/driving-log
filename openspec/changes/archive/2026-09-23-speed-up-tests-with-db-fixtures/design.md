# Design

## Context

Today every Maestro flow builds its own state through the UI: `add-vehicle.yaml` (a subflow, run by most flows) adds
a vehicle by filling the form, and flows that need logged events add them one at a time through the log event form.
`maestro/assets/`'s test photos are the one place this project already uses *prepared* data instead of building it
live — a manifest's `setup.yaml` uploads them once via Maestro's `addMedia` command (into the device's shared media
store, which the system photo chooser then offers). That existing pattern only reaches the **shared media store**;
nothing today puts data directly into the app's own private storage (its SQLite database, its private picture
files) ahead of a flow running.

`SqlDelightVehicleRepositoryTest` (`shared/src/androidHostTest`) already proves the mechanism a fixture generator
needs: it runs `SqlDelightVehicleRepository` — the exact class the shipped app uses — against SqlDelight's JVM/JDBC
driver (`createTestDriver()`), off-device, in a unit test. Generating a fixture `.db` file is the same thing, run
once as a build task instead of once per test.

`ImageCodec` (decode/scale/encode) has **no JVM implementation** — only `AndroidImageCodec` and `IosImageCodec`
exist, both built on platform-only graphics APIs. A fixture generator cannot run the real encode pipeline for
pictures the way it can for database rows.

See proposal.md for the motivation and scope; see the `test-strategy` spec delta for the exact required behavior.

## Goals / Non-Goals

**Goals:**
- Let a Maestro flow whose subject is "how is this rendered" start from a database already in the needed state,
  without driving the UI to build it.
- Keep fixture data exactly as valid as UI-entered data would be, for the database (by generating it through the
  real repository code) — not hand-written SQL that can silently drift from the schema.
- Leave a fixture-seeded flow's resulting state on the device after the run, for inspection.

**Non-Goals:**
- Replacing existing UI-driven flows. A flow whose subject *is* the UI path that builds the state (adding a vehicle,
  logging an event) keeps building it through the UI — that is what it is testing.
- Running the real `ImageCodec` pipeline to produce fixture pictures (no JVM implementation exists; see Context).
  Fixture pictures are static, valid image files, not proof that encoding works — that is `ImageCodec`'s own unit
  tests' job.
- Any change to app runtime code. This is entirely test tooling.

## Decisions

### Fixture `.db` files are generated by running the real repository code on the JVM, checked in as versioned assets
A new Gradle task (JVM target) runs a small Kotlin program per named fixture (e.g. `vehicle-with-log-and-note`):
construct `SqlDelightVehicleRepository` against a fresh SQLite file via the JDBC driver (identical setup to
`SqlDelightVehicleRepositoryTest`), call the same `addVehicle`/`addDistanceEntry`/`addOdometerAnchor` methods a real
flow would trigger through the UI, close the driver, and copy the resulting file to
`maestro/assets/fixtures/<name>.db`. The task is run on demand (when a fixture's scenario changes, or the schema
migrates) and its output is checked in, the same way `maestro/assets/`'s test photos are checked-in prepared data
rather than generated at test time.

Alternative considered: hand-written `INSERT` SQL (or a `.sql` seed script) maintained alongside the schema.
Rejected: it duplicates knowledge the schema and the domain layer already encode (id formats, foreign keys, which
columns a given event type actually uses) and drifts silently — a migration can leave a hand-written seed script
producing rows the real app would never write, with nothing to catch it. Running the real repository code makes
that class of drift impossible: a fixture is only ever built from calls the production code itself validates.

### Picture fixtures are static, hand-prepared assets, not generated
Since no JVM `ImageCodec` exists, a vehicle's (and, once `add-event-pictures` lands, an event's) fixture picture
files are ordinary small/large image files prepared once by hand (or with any offline tool) and checked into
`maestro/assets/fixtures/` alongside the `.db` files, sized to the same conventions `vehicle-picture`/`event-pictures`
document (at most 256px / at most 1024px or 2048px). The `.db` generator writes the *id* these files are named by
into the relevant row (`vehicle.picture_id`, `event_picture.id`), so the database and the picture files agree by
construction. This is sufficient for the goal (checking how a picture renders), which does not depend on the file
having passed through the real encoder.

### Device placement: stop the app, `adb push` to a staging path, `run-as` to copy into private storage, then launch without `clearState`
Private app storage (`/data/data/<package>/...`) cannot be written by a plain `adb push` on a non-rooted
device/emulator; `run-as <package> cp ...` from a world-readable staging location (`/data/local/tmp`) is the
standard mechanism for a debuggable build, which the debug APK already is. The sequence, in order, matters:
1. `adb shell am force-stop com.mikonoma.drivinglog` — the app must not hold the database open while its file is
   replaced underneath it.
2. `adb shell pm clear com.mikonoma.drivinglog` — establishes a known-empty starting point, the same guarantee
   `launchApp: { clearState: true }` gives a UI-driven flow, so a fixture-seeded flow's result does not depend on
   whatever an earlier run left behind.
3. `adb push` the fixture `.db` and picture files to `/data/local/tmp/`, then `run-as ... cp` each into place (the
   database directory, the picture store's root).
4. Launch the app. **Its own `launchApp` step in the flow's `.yaml` must use `clearState: false` (or omit
   `clearState`)** — `clearState: true` here would immediately wipe what step 3 just placed, silently defeating the
   whole mechanism. This is the one footgun of the design and is called out explicitly in the how-to doc (task 5).

Steps 1-3 cannot be expressed inside a Maestro `.yaml` flow (it has no generic "run a shell command" step), so they
run in a wrapper script (`maestro/seed-fixture.sh <fixture-name>`) invoked *before* `maestro test` for that flow —
extending `run.sh`'s existing per-flow orchestration (it already assembles a custom flow list for `run.sh <area>
<flow>`; a flow paired with a fixture is the same idea, seeding instead of, or before, a `setup.yaml`). A flow
declares which fixture it needs via a companion file (`<flow>.fixture`, one line: the fixture name) that `run.sh`
checks for next to the flow before running it, so the association lives next to the flow it belongs to rather than
in `run.sh` itself.

### No cleanup after the flow runs
Unchanged from a UI-driven flow's own behavior today (which also leaves its data for the *next* run's `clearState:
true` to overwrite, not for that run's own end): a fixture-seeded flow simply stops after its assertions. Its
resulting state — whatever the flow's own steps changed — stays on the device exactly as the flow left it, so a
failure's on-device state can be inspected afterward without re-running anything.

### One fixture is reused by every case it already covers, not duplicated per flow
Per the developer's explicit direction: before adding a new named fixture, an existing one that already holds the
needed state is reused — a new *case* (in an existing flow, or a new flow that seeds the same fixture) rather than
a near-duplicate fixture with slightly different data. `docs/test-fixtures.md` keeps a table of every fixture and
what uses it specifically so this is checkable before adding one. The fewer fixtures there are, the less there is
to keep in sync with the schema (see `FixtureFreshnessTest` above) and the more of `GenerateFixtures.kt`'s
scenario-building code is shared rather than copy-pasted.

## Risks / Trade-offs

- **[Risk]** `run-as` requires the target build to be debuggable and the emulator/device to allow it → **Mitigation**:
  every device this project's Maestro suite already runs on is the debug build on an emulator/device set up for
  testing; not a new constraint.
- **[Risk]** A fixture `.db` can go stale relative to the schema (a migration adds a column the fixture generator's
  scenario never touches, say) → **Mitigation, strengthened during implementation**: not just documentation —
  `FixtureFreshnessTest` (`shared/src/androidHostTest`) runs as part of the ordinary test suite and opens every
  checked-in fixture, asserting its stamped `PRAGMA user_version` still matches `DrivingLogDatabase.Schema.version`.
  A migration that outpaces the fixtures fails this fast, JVM-only test immediately, with a message naming the
  fix (`./gradlew :shared:generateMaestroFixtures`) — not, mysteriously and much later, a Maestro flow on a device.
  This was prompted directly by discovering, while building this change, that a *stale-in-the-other-direction* bug
  (a fixture generated without stamping the version at all) silently broke the app's reactive queries on-device
  with no error surfaced anywhere obvious — exactly the failure mode this test now catches at the source.
- **[Risk]** The `clearState: false` requirement is easy to get wrong when writing a new fixture-seeded flow →
  **Mitigation**: called out explicitly in the how-to documentation and in a fixture-seeded flow's own header
  comment convention (task 5); no way to enforce it mechanically without teaching `run.sh` to inspect the flow's
  YAML, which is more machinery than this risk currently justifies.
