# Proposal

## Why

Many Maestro flows spend most of their steps re-creating state through the UI (adding a vehicle, logging several
events) purely so a *later* step can check how something renders — the recent-events list, the details screen, the
row icons. That setup is slow, and it duplicates what the compose/write path's own unit tests (and, once adopted,
Compose integration tests) already check. A flow whose actual subject is "how is this shown" should be able to start
from a database already in the state it needs, the same way `maestro/assets/`'s test photos are already prepared
data rather than something each flow builds by hand.

## What Changes

- A new, offline, JVM-run Gradle task generates named fixture files for known test scenarios (e.g.
  `vehicle-with-log-and-note`), using the real `SqlDelightVehicleRepository`/domain code (the same one
  `SqlDelightVehicleRepositoryTest` already runs on the JVM via SqlDelight's JDBC driver) so a fixture's data is
  exactly as valid as data a real app flow would produce — never hand-written SQL that can drift from the schema.
  The generated `.db` file is checked into `maestro/assets/fixtures/` as a versioned asset, regenerated by that task
  whenever a fixture's scenario or the schema changes.
- Picture fixtures (a vehicle's picture, and once `add-event-pictures` lands, an event's photos) are **not**
  generated by that task — there is no JVM implementation of `ImageCodec` (it is Android/iOS-only), and a
  rendering-focused flow does not need its fixture picture files to have passed through the real encode pipeline,
  only to be valid, correctly-sized small/large image files. They are static, hand-prepared binary assets checked
  into `maestro/assets/fixtures/` alongside the `.db` files, referenced by the picture ids the `.db` generator
  writes into the database.
- A new script pushes a named fixture's `.db` and picture files onto a running emulator/device, into the app's
  private storage (`adb push` to a staging path, then `run-as` to copy into place — private app storage cannot be
  written directly). A flow that wants a fixture starts: stop the app if running, push and place the fixture files,
  then launch the app **without** `clearState` (state is already exactly what the fixture set it to). No separate
  reset step exists elsewhere in the flow for this.
- No cleanup after the flow runs. Unlike the existing UI-driven flows (which already leave their data for the next
  run to overwrite via `clearState: true`), a fixture-seeded flow's resulting device state is left as-is
  deliberately, so a failure can be inspected afterward exactly as the flow left it.
- Existing UI-driven flows are unaffected; this is an additional way to start a flow, used only where a flow's
  purpose is checking rendering, not checking that the UI itself can produce that state (the two remain separate
  concerns per `test-strategy`'s existing "Maestro flows are happy paths" requirement — a fixture-seeded flow still
  follows one real journey afterward, it just starts further along).

## Capabilities

### Modified Capabilities
- `test-strategy`: adds fixture-seeded flows as a second, additional way a Maestro flow may establish its starting
  state, alongside (not instead of) the existing UI-driven and photo-upload setup patterns.

## Impact

- New Gradle task (JVM) generating `.db` fixture files from the real repository code.
- New static picture fixture assets under `maestro/assets/fixtures/`.
- New `maestro/seed-fixture.sh <fixture-name>` (or similar), doing the stop-app/push/place sequence.
- `docs/test-strategy.md`: documents the fixture-seeding pattern alongside the existing manifest/setup one.
- No app runtime code changes — this is entirely test tooling.
